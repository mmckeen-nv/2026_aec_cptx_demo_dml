# Cliff House compatibility entry point

Project memory namespace: `project:cliff-house-01`.

The canonical Cliff House workflow runs from repository root, exactly like the
pristine control. If this directory is opened directly, first read:

1. `../../system_prompts/00_session_startup.md`
2. `../../skills/INDEX.md`
3. `../../skills/session_state.md`
4. `../../aa_demo_versions/cliff_house_02/user_prompts/project_prompt.md`
5. `../../hermes/DEMO_RULES.md`
6. `../../deployment/aec-cptx-profile/canonical-cliff-house-geometry.txt`
7. only the current numbered phase prompt under `../../system_prompts/`

Manual mode preserves the original pacing: one visible object per MCP call, a
short unannounced pause between objects, narrow phase scope, review gate, and
named checkpoint.

When the operator says "Run the Cliff House build automatically" or an
unambiguous equivalent, read
`../../deployment/aec-cptx-profile/cliff-house-automatic-run.txt` and execute
its optimized continuous form of the same canonical workflow. Automatic mode
uses phase-level Rhino scripts and the validated Blender fast path. It is an
automatic run, not a benchmark. Do not expose benchmark terminology to the
operator.

Both modes must apply the shared canonical geometry, site-grading, furniture,
camera, Blender 5.2, tagged-terrain-removal, direct-FLUX.2, and validation
corrections. Daystrom DML supplies advisory continuity and compact validated
lessons; it does not gate calls.

The launcher owns application lifecycle. Never spawn/close Rhino slots, close
or reopen the active document, or launch/repair Blender from the run.
